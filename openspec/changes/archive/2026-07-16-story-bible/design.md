## Context

事实库是本系统的“活的符号表”，把长篇剧情沉淀为可结构化查询的强约束事实，用以机械化地检出
命名漂移、时间线断层、人设崩塌、伏笔悬空等长篇“编译期 bug”。它必须动态生长、可溯源、可版本化，
并支持正向与反向双向检查。本 change 只定义数据模型与检查契约，不实现 agent 编排与总检调度。

出处锚点直接复用 story-workspace 的稳定标识符（卷/章/场景 id + 文本片段），确保正文编辑后锚点不漂。

## Goals / Non-Goals

**Goals:**
- 定义可承载人物/地点/物品/组织、其属性、时间线、关系、伏笔状态的结构化事实模型。
- 每条事实可溯源（出处锚点 + 置信度）、有状态（confirmed/inferred/conflicting）。
- 事实库版本化并与编排 checkpoint 对齐，支持随正文回滚；写入为增量而非覆盖。
- 支持从正文增量抽取候选事实，低风险自动入库、冲突挂起人工确认。
- 支持正向检查（新文对撞库）与反向检查（改库后扫全书），输出统一的结构化一致性问题。

**Non-Goals:**
- 不实现执行检查的 agent 及其在图中的编排（agent-orchestration）。
- 不实现全书 Map-Reduce 总检的调度与仪表盘（global-audit）。
- 不实现素材/灵感提炼（corpus-library）。
- 不决定“改设定还是改旧文”——冲突时把决策交还作者（人工决策标记），本 change 只产出问题与选项。
- 不编写实现代码。

## Decisions

### D1. 事实模型：实体–属性 + 时间线 + 关系 + 伏笔
- **实体（Entity）**：类型化（人物/地点/物品/组织/其他，可扩展），有稳定 id 与规范名。
- **属性（Attribute）**：隶属实体的键值事实（性格、能力、习惯、外貌、**称呼别名**等）。称呼别名尤为
  关键——“顾长风/顾兄弟/姑爷”构成合法称呼集合，集合外的称呼（如“九爷”）即疑似未声明符号。
- **时间线（Timeline）**：单向自增的故事内时序锚，事件可挂接到时序点；用于检出“7 天断流”“枪伤后
  立即健步如飞”等时序矛盾。
- **关系（Relation）**：实体间的有向/无向关系（敌对、亲属、上下级等），可随剧情演变（带时序）。
- **伏笔（Plot Hook）**：显式状态机——埋设（planted）→ 待回收（pending）→ 已回收（paid_off）
  →（可选）作废（abandoned）；用于检出“悬空伏笔”。

### D2. 出处锚点与置信度
- 每条事实 MUST 记录一个或多个来源，每个来源含：章/场景稳定标识符、文本片段（引文）、置信度。
- 锚点复用 story-workspace 的稳定标识符，正文编辑不使锚点失效（章级恒定；片段用于人工核对）。
- 反向检查报冲突时，MUST 能同时给出“新事实来源”与“被冲突旧描写来源”两个锚点，便于作者跳转比对。

### D3. 事实状态与自动/人工边界
- 状态：`confirmed`（作者确认，最高权威）、`inferred`（AI 抽取推断）、`conflicting`（与既有事实冲突）。
- **自动入库**：新出现且不与既有事实冲突的低风险事实（如首次出现的人名）MUST 自动入库并标 `inferred`。
- **挂起人工确认**：与既有事实冲突、或高风险的事实 MUST 标记为 `conflicting` 并挂起，交作者裁决。
- `confirmed` 事实优先级高于 `inferred`；冲突裁决可将某方升为 `confirmed` 或修正之。
- 目标：避免十万字创作中数百次打断，仅在真正冲突处请求作者介入。

### D4. 版本化与 checkpoint 对齐
- 事实库写入 MUST 为**增量 + 版本标记**，MUST NOT 覆盖历史（保留“何时由何来源引入”）。
- 事实库版本 MUST 与编排的 checkpoint 对齐：当正文/运行 time-travel 回滚到某 checkpoint 时，
  事实库 MUST 能呈现该 checkpoint 时刻的一致视图。
- 依据：若正文回退而事实库仍保留后来才引入的设定，双向检查将失真。
- 与 checkpoint 的具体绑定机制由 agent-orchestration/human-in-the-loop 提供的 checkpoint 标识对接，
  本 change 定义“事实版本须可关联 checkpoint 标识并按其还原”的契约。

### D5. 增量抽取
- 输入：一段新产出或新导入的正文（含其章/场景标识符）。输出：候选事实集合（含建议锚点与置信度）。
- 抽取结果按 D3 规则入库；抽取属模型调用，其 prompt/agent 由 agent-orchestration 装配，本 change
  仅定义抽取的输入/输出契约与合并/入库策略。
- 抽取 MUST 保证幂等友好：对同一来源重复抽取不产生重复矛盾的事实堆积（以来源锚点去重/更新）。

### D6. 正向一致性检查
- 输入：一段（新）正文 + 事实库当前版本视图。输出：结构化一致性问题列表。
- 典型检出项：称呼/命名冲突（集合外称呼）、时间线断层、行为 OOC、状态矛盾（物品/信息持有者错误）、
  空间走位矛盾、伏笔相关异常。
- 正向检查是“拿新文查库”，用于写完/召唤审计时即时反馈。

### D7. 反向一致性检查（涟漪效应）
- 触发：某事实被新增/修改（尤其 `confirmed` 变更）。
- 行为：检索所有引用相关实体/属性的已有章节（借助锚点与语义检索定位候选），逐一比对，报告被新事实
  破坏的旧描写。
- 输出：一致性问题列表，每项含“新事实”与“冲突旧文”双锚点。
- 大规模检索/比对若属 CPU 密集，MUST 在 utilityProcess 执行；SQLite 读写作为异步 I/O 归 Main。

### D8. 一致性问题模型（统一契约）
- 每个问题 MUST 含：`type`（命名/称呼冲突、时间线断层、行为 OOC、伏笔悬空、状态矛盾、空间走位、其他）、
  `severity`（如 critical/warning/info）、`anchors`（一个或多个稳定标识符定位）、`description`、
  `suggestedFix`（可空）、`requiresHumanDecision`（布尔）。
- `requiresHumanDecision=true` 的问题（如反向冲突“改设定还是改旧文”）MUST 附带可选项，由系统呈现、
  作者裁决；系统 MUST NOT 自行选择。
- 该模型是 agent-orchestration（审稿/纠 bug）、on-demand-summon（召唤审计官）、global-audit
  （总检红黄牌）共用的输出契约。

## Risks / Trade-offs

- **风险：AI 抽取的事实有噪声/错误。** 缓解：inferred 状态 + 出处锚点 + 作者可随时修正；冲突才打断。
- **风险：反向全书扫描开销大。** 缓解：借助锚点与语义检索缩小候选集，CPU 密集部分入 utilityProcess；
  触发时机由上层（定稿/手动体检）控制，本 change 只保证能力可用与不阻塞 UI。
- **风险：事实库版本与 checkpoint 对齐的耦合。** 取舍：定义为“可关联 checkpoint 标识并按其还原”的
  松契约，具体 checkpoint 由编排层提供，避免两个子系统硬绑定。
- **权衡：自动入库降低打断频率但引入噪声。** 取舍：以状态分级 + 可溯源 + 冲突才确认平衡“省心”与“可信”。
