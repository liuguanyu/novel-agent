## Context

用户的两种起点（导入既有废稿 / 全新创作）都必须一等支持。本项目自带示例 `津门余味` 即典型的
“已散落在文件系统中的多章节 Markdown 稿”。工作区是承载一本书的容器，也是事实库、素材库、编排、
总检等一切能力的数据基座。本 change 只定义数据模型与导入/存储契约，不做事实抽取与素材提炼。

## Goals / Non-Goals

**Goals:**
- 定义“一本书 = 一个本地项目工作区”的模型与元数据。
- 定义正文的章节树结构与**稳定标识符**，使 bug 定位、事实溯源、diff 能长期引用同一锚点。
- 支持全新创作（空工作区）与导入既有 Markdown 小说两种起点。
- 定义导入解析契约，包括边界识别、原文保真、歧义与失败的人工确认降级。
- 定义人类可读、可手改、可版本管理的磁盘存储布局。

**Non-Goals:**
- 不从正文抽取结构化事实（由 story-bible 负责）。
- 不提炼灵感/高光/桥段（由 corpus-library 负责）。
- 不涉及编辑器 UI 与渲染（由 electron-shell-ui 负责）。
- 不涉及任何模型/AI 调用。
- 不编写实现代码。

## Decisions

### D1. 项目粒度：一本书一个本地项目
- 一个工作区对应一本书，含元数据（书名、体裁、语言、简介、目标读者等，字段可扩展）。
- 工作区自包含：正文、章节树、元数据均在同一项目目录下，便于备份与版本管理。
- 事实库（SQLite）、素材库挂载点等由各自 change 定义其在项目内的位置，本 change 只预留布局约定。

### D2. 章节树弹性层级 + 稳定标识符
- 结构层级：卷（Volume，可选）/ 章（Chapter，必需）/ 场景（Scene，可选）。
  - **章是唯一必需层级**；卷（章之上的分组）与场景（章内的细分）均可选。
  - 短篇/不分卷的作品可将章直接置于顶层；未切分场景的章只到章级。
- 每个节点（卷/章/场景）MUST 具备**稳定且唯一的标识符**，与其标题、顺序、正文内容解耦：
  - 重命名标题、调整顺序、编辑正文均 MUST NOT 改变标识符。
  - 该标识符是 bug 定位、事实出处锚点、diff 目标、time-travel 的长期引用基础。
- 正文以章为基本存储单元；场景为章内的逻辑切分。

### D3. 两种起点统一收敛到同一工作区模型
- **全新创作**：创建空工作区，仅有元数据，章节树为空或含占位；后续由作者/agent 逐步填充。
- **导入既有小说**：解析既有 Markdown 目录 → 生成章节树与正文 → 落为标准工作区。
- 两条路径终点一致：一个符合 manuscript-model 的工作区。下游能力无需区分来源。

### D4. 导入解析：保真优先 + 歧义人工确认
- 解析 MUST 保留原始正文内容（保真），不得在导入阶段擅自改写、润色或“修复”。
- 边界识别策略：基于 Markdown 标题层级与文件组织推断卷/章边界（如目录=卷、文件=章，或标题级别映射）。
- 歧义或识别失败时 MUST 降级为向用户呈现推断结果并请求确认/手工调整，而非静默猜测。
- 导入 MUST 记录来源路径，便于回溯与再导入。
- 大文档解析属 CPU 密集，MUST 在 utilityProcess 执行（遵循 process-model）。

### D5. 存储布局：人类可读、可手改、可 diff
- 正文以 Markdown 落盘，结构与元数据以显式、可读的形式存储（避免不可读的二进制黑盒）。
- 布局 MUST 支持用户在编辑器外直接查看与手工修改，并对版本控制（如 Git）友好。
- 稳定标识符 MUST 以某种对用户无破坏、对工具可解析的方式持久化（例如与文件映射的清单，
  或 front-matter），具体形式在实现阶段确定，但须满足 D2 的“重命名/移动不丢标识”。

## Risks / Trade-offs

- **风险：不同作者的 Markdown 组织习惯差异极大，解析难以通用。** 取舍：以“保真 + 歧义人工确认”
  兜底，宁可让用户确认，不做危险的静默猜测。
- **风险：稳定标识符与人类可读文件布局之间存在张力**（用户手动改文件可能破坏映射）。取舍：选择
  对用户改动尽量鲁棒的映射方式，并允许重建映射；不为标识符牺牲可读性。
- **权衡：卷与场景层级均可选，增加模型灵活性但也增加下游处理分支。** 取舍：保留“章为唯一必需层级、
  卷与场景可选”，下游统一按“章为主，卷为可选分组、场景为可选细分”处理。
