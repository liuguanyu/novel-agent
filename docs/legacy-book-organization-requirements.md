# 老书整理 v2 产品需求文档

> 状态：需求基线草案
> 更新时间：2026-08-05
> 适用范围：已有正文的老书整理
> 本文档不使用 OpenSpec；产品、设计和实现讨论均以本文档为当前基线。

## 1. 背景

当前老书功能以“发现问题并逐个修复”为主线：系统先建立事实底稿、执行全书诊断，再围绕问题完成定位、改写、审阅、写入、复检和关闭。

这条链路具备事实抽取、原文定位、安全改写和版本恢复等有效能力，但不符合作者整理老书时的主要心智：

- 作者打开老书功能时，已经决定要继续整理，不需要系统判断“值不值得救”。
- 作者首先需要重新看清旧稿的结构，而不是先接收问题清单。
- 作者关心哪些核心情节和原话需要保留，以及新版大纲准备如何组织。
- 大量局部问题无法代替全书结构调整。
- 正文调整应该服务于作者确认后的新版大纲，而不是由问题列表驱动。

因此，老书产品主线需要从“问题修复”转为“旧稿整理”。

## 2. 产品定义

### 2.1 一句话定义

帮助作者重新梳理旧稿，留下想留下的内容，整理出新版大纲，再决定正文如何调整。

### 2.2 核心产品闭环

```text
旧稿正文
→ 还原旧稿大纲
→ 标记保留情节与保留原文
→ 整理新版大纲
→ 按作者选择调整正文
→ 通读并确认修订稿
```

### 2.3 核心产品资产

老书整理的核心资产是：

1. **旧稿大纲**：系统从现有正文还原出的故事结构。
2. **保留内容**：作者明确要求继续存在的核心情节和原文。
3. **新版大纲**：作者在旧稿和保留内容基础上整理出的新结构。
4. **修订稿**：按照新版大纲调整、且与原稿相互独立的正文版本。

其中，“保留内容 + 新版大纲”是产品中心。诊断问题、事实库和一致性检查均为辅助能力。

## 3. 已确认的产品决策

以下内容视为本阶段已确认，不再作为待讨论前提：

1. 不判断一本书是否值得整理。作者打开该功能即代表有整理意愿。
2. 产品统一使用“整理”，不使用“救书”“写崩”等评价性表达。
3. 不要求系统分析或解释“为什么写崩”。
4. 第一核心任务是还原旧稿大纲，并帮助作者明确：
   - 哪些核心情节要保留；
   - 哪些原话要保留。
5. 问题列表不再作为老书整理主入口或主要工作单位。
6. 新版大纲确认前，不应直接推动作者逐问题修改正文。
7. 正文调整不是强制阶段；作者可以只完成旧稿梳理和新版大纲。
8. 原稿始终保留，整理过程不得静默覆盖原稿。
9. AI 对大纲和正文的修改必须先给出建议或草案，再由作者应用。
10. 现有底层能力继续复用，但不能再决定顶层产品结构。

## 4. 产品目标

### 4.1 用户目标

作者使用产品后，应能够：

- 快速看清旧稿当前讲了什么，以及各部分如何组织；
- 从旧稿中标记必须保留的核心情节；
- 从正文中选择必须保留的原话；
- 在保留约束下生成并编辑新版大纲；
- 随时知道保留内容是否已经在新版大纲中得到安排；
- 自主选择哪些大纲节点需要调整正文；
- 在不覆盖原稿的前提下生成、审阅和采用修订稿；
- 通读修订稿，并自行决定哪些建议处理、接受或留待以后。

### 4.2 产品体验目标

作者在任意时刻都应能够回答：

1. 我现在看的是原稿、旧稿大纲、新版大纲，还是修订稿？
2. 哪些情节和原话已经标记保留？
3. 保留内容在新版大纲中安排到了哪里？
4. 当前正在整理或调整哪个情节？
5. 系统准备修改什么，不会修改什么？
6. 是否需要我确认？
7. 如果不满意，能否撤销或恢复？

### 4.3 业务目标

- 建立以大纲为中心的老书整理闭环。
- 将已有事实抽取、定位、改写、差异审阅和版本能力转为大纲工作流的支撑能力。
- 降低作者面对大量诊断问题时的认知负担。
- 为后续支持人物线、关系线、伏笔和设定整理保留扩展空间。

## 5. 非目标

本阶段不包括：

- 评价作品质量或判断是否值得继续整理；
- 自动分析“写崩原因”并要求作者接受结论；
- 以健康分、红黄牌或问题清零作为完成标准；
- 自动覆盖原稿；
- 未经作者确认直接应用 AI 生成的大纲或正文；
- 第一版同时支持人物、设定、氛围、写作风格等复杂保留类型；
- 第一版实现自由画布式大纲；
- 强迫作者完成全部正文调整或处理全部整理建议；
- 立即删除现有 issue 工作流及其历史数据。

## 6. 信息架构

### 6.1 一级工作区

老书整理提供四个一级工作区：

```text
旧稿梳理 | 新版大纲 | 正文调整 | 通读
```

它们是可随时切换的工作空间，不是严格不可逆的线性步骤。

### 6.2 辅助入口

以下能力作为辅助入口存在，不与四个工作区争夺主位：

- **资料**：人物、关系、设定等 Story Bible 内容；
- **建议**：由诊断和一致性检查产生的整理建议；
- **版本**：新版大纲和修订稿的版本历史。

### 6.3 工作区职责

| 工作区 | 回答的问题 | 核心产物 |
|---|---|---|
| 旧稿梳理 | 旧稿现在写了什么？什么不能丢？ | 旧稿大纲、保留内容 |
| 新版大纲 | 新版故事准备怎么组织？ | 已确认的新版大纲 |
| 正文调整 | 哪些正文需要按照新大纲调整？ | 修订稿 |
| 通读 | 修订稿作为完整作品读起来如何？ | 作者确认的定稿版本 |

## 7. 核心对象

本节定义产品语义，不约束最终代码命名。

### 7.1 旧稿大纲

系统从原稿还原的层级结构，至少包含：

- 卷或部分；
- 主要情节节点；
- 节点标题和摘要；
- 来源章节；
- 涉及的主要人物；
- 可定位的原文来源。

旧稿大纲是系统对原稿的整理结果，不直接修改原稿。

### 7.2 大纲节点

新版和旧稿大纲的基本工作单位。第一版推荐层级：

```text
卷或部分
└── 情节段
    └── 关键情节
```

第一版不要求细化到每一个场景。

大纲节点至少包含：

- 标题；
- 一句话摘要；
- 上下级与排序关系；
- 来源类型；
- 原稿来源；
- 关联保留内容；
- 作者说明；
- 正文调整状态（新版节点适用）。

### 7.3 保留情节

含义：该情节在新版中必须存在，但允许作者调整位置、铺垫、表达方式和具体写法。

第一版需要支持：

- 从旧稿大纲节点标记；
- 添加作者说明；
- 跳回原稿来源；
- 取消保留；
- 检查是否已经安排到新版大纲。

### 7.4 保留原文

含义：作者选定的文字内容默认保持不变，但允许安排到新版中的其他位置。

第一版需要支持：

- 从系统推荐原文中选择；
- 从原稿正文主动框选；
- 记录精确文字和原稿位置；
- 添加作者说明；
- 关联到旧稿或新版大纲节点；
- 检查在大纲和修订稿中的安排情况；
- 由作者明确取消保留。

### 7.5 新版大纲

作者在旧稿大纲、保留内容和补充要求基础上形成的可编辑大纲。

节点与旧稿的关系至少区分：

- 沿用原稿；
- 调整原稿；
- 合并原稿；
- 新增。

### 7.6 正文调整单元

一次正文调整所服务的新版大纲节点。它可以引用一个或多个原稿章节、片段和保留内容，并产生对应修订稿内容。

正文调整的业务入口是新版大纲节点，而不是诊断问题。

### 7.7 整理建议

由诊断、一致性检查或大纲分析产生的辅助建议。建议必须关联到可操作的业务位置，如大纲节点、正文节点、人物或设定。

建议状态第一版仅需：

```text
待查看 | 已处理 | 暂不处理
```

## 8. 核心用户流程

### 8.1 首次整理

```text
打开老书
→ 开始整理旧稿
→ 系统还原旧稿大纲和候选保留内容
→ 作者查看旧稿结构
→ 作者标记保留情节和保留原文
→ 生成新版大纲草案
```

### 8.2 整理新版大纲

```text
查看系统草案
→ 编辑、移动、新增、删除、合并或拆分节点
→ 查看节点原稿来源
→ 检查保留内容覆盖情况
→ 作者确认当前大纲版本
```

### 8.3 按需调整正文

```text
选择需要调整的新版大纲节点
→ 确认来源、目标和保留内容
→ 生成调整稿
→ 阅读、编辑或重新生成
→ 必要时查看原稿对照和逐处变化
→ 写入修订稿
→ 更新节点调整状态
```

### 8.4 通读定稿

```text
阅读修订稿
→ 查看就地整理建议
→ 现在调整、接受现状或留到以后
→ 确认定稿版本
```

### 8.5 只整理大纲

作者可以在确认新版大纲后结束本次工作：

```text
旧稿梳理
→ 新版大纲确认
→ 保存或导出大纲
→ 暂不调整正文
```

该路径必须是正常完成方式，不应被表现为流程中断。

## 9. 页面与交互需求

## 9.1 书籍入口

首次进入时展示：

- 当前书名；
- “整理旧稿”的主标题；
- 将生成的内容：当前故事大纲、核心情节、关键原文、人物关系和重要设定；
- “原稿不会被修改”的安全说明；
- 主操作“开始整理”；
- 次操作“直接阅读原稿”。

不得展示：

- 是否值得整理；
- 健康分；
- 问题总数；
- 红牌或黄牌；
- 内部工作流阶段。

再次进入时展示：

- 上次所在工作区；
- 保留情节和保留原文数量；
- 新版大纲版本与确认状态；
- 正文调整完成情况；
- 主操作“继续整理”。

## 9.2 整理运行状态

整理任务运行时，作者看到业务进度：

```text
读取正文
整理现有大纲
整理核心情节和关键原文
整理人物、关系和设定
```

要求：

- 进度必须来自真实任务状态，不伪造百分比；
- 作者可以离开页面并在后台继续；
- 顶部提供持续可见的后台状态；
- 完成后展示整理出的卷、主要情节、候选保留内容和主要人物数量；
- 不暴露模型 run、内部阶段 ID 或事实版本 ID。

## 9.3 旧稿梳理工作区

### 布局

宽窗口采用三栏：

```text
旧稿结构 | 旧稿大纲或原稿正文 | 当前情节详情
```

中等窗口隐藏常驻详情栏，改为右侧抽屉；窄窗口使用“结构 / 内容 / 详情”单栏切换。

### 旧稿结构栏

至少支持：

- 按卷、章导航；
- 搜索正文；
- 按人物筛选；
- 只看已保留内容；
- 只看有关键原文的内容；
- 只看尚未查看或已加入新版大纲的内容。

### 旧稿大纲

节点卡片至少展示：

- 标题和摘要；
- 来源章节；
- 主要人物；
- 是否已保留；
- 关键原文数量；
- 是否已加入新版大纲。

节点操作至少包括：

- 查看原稿；
- 保留情节或取消保留；
- 选择保留原文；
- 加入新版大纲。

### 原稿阅读联动

- 从大纲节点可以跳到对应原稿；
- 原稿默认只读；
- 作者框选文字后显示“保留原文”；
- 已保留原文在原稿中有轻量标记；
- 点击标记可以查看所属情节和作者说明。

### 当前情节详情

至少展示：

- 情节标题和摘要；
- 来源章节；
- 涉及人物；
- 关键原文候选；
- 当前保留状态；
- 查看原稿、保留情节、保留原文和加入新版大纲操作。

## 9.4 保留内容抽屉

全局常驻摘要：

```text
已保留 X 个情节 · Y 处原文
```

抽屉内按“情节”和“原文”分组，每项支持：

- 查看内容；
- 跳转原稿；
- 查看或修改作者说明；
- 查看在新版大纲中的安排位置；
- 取消保留。

保留内容不得在标记后从主流程中消失。

## 9.5 生成新版大纲

生成前允许作者提供最少必要边界：

- 整理全书、指定卷或选中内容；
- 原结局暂时保留、可以调整或尚未决定；
- 可选补充要求。

要求：

- 未标记保留内容时可以继续生成，但需要轻量提示；
- 生成结果必须作为草案，不直接覆盖作者已有大纲；
- 生成完成后总结旧稿节点数量变化、保留内容安排情况和尚未安排项；
- 作者明确进入新版大纲后才将草案作为当前编辑对象。

## 9.6 新版大纲工作区

### 布局

宽窗口采用：

```text
旧稿素材 | 新版大纲编辑器 | 当前节点详情
```

### 大纲编辑器

第一版采用层级树形列表，不使用自由画布。

至少支持：

- 新增节点；
- 编辑标题和摘要；
- 拖动排序；
- 移动到其他卷或情节段；
- 删除；
- 合并；
- 拆分；
- 从旧稿素材加入；
- 查看原稿来源；
- 撤销和重做。

### 节点来源

每个节点必须显示以下来源之一：

```text
沿用原稿 | 调整原稿 | 合并原稿 | 新增
```

来源节点可追溯到原稿章节或片段。

### 保留覆盖状态

顶部持续展示：

```text
X/X 个保留情节已安排 · Y/Y 处保留原文已安排
```

尚未安排项必须可直接查看并安排到大纲。

删除含保留内容的节点时：

- 明确原稿不会被删除；
- 明确保留内容将变为“尚未安排”；
- 允许作者取消、移动保留内容后删除，或知情删除节点。

### AI 调整

至少支持针对选中节点：

- 重新组织；
- 合并；
- 拆分；
- 补充前因；
- 补充后果；
- 提供另一种安排。

AI 调整必须先展示计划和大纲级变化预览，再由作者应用。不得静默修改当前大纲。

### 确认大纲

确认前展示：

- 当前版本；
- 节点数量；
- 保留内容覆盖状态；
- 尚未安排内容。

允许作者在有尚未安排内容时知情确认。

确认后仍允许修改；如果修改影响已完成正文，相关正文节点标记为“需要重新对应”，正文不得自动改变。

## 9.7 正文调整工作区

### 进入方式

作者确认新版大纲后，可以：

- 开始调整正文；
- 暂时完成，只保存或导出大纲。

进入正文调整时，作者可以选择：

- 按新版大纲逐段调整；
- 只调整变化较大的部分；
- 自己选择节点。

### 节点状态

正文调整节点使用：

```text
未安排 | 无需调整 | 准备调整 | 调整中 | 待确认 | 已完成 | 需要重新对应
```

技术任务失败不得永久改变创作节点状态，应单独提示“生成失败，可重试”。

### 生成调整稿前

必须展示：

- 当前新版大纲节点；
- 将参考的原稿章节和片段；
- 新版要求；
- 必须保留的情节和原文；
- 写入修订稿的位置；
- 可能影响的后续节点；
- “原稿不会被修改”。

写入位置不明确时，必须由作者确认。

### 调整稿审阅

默认提供三种视图：

```text
调整稿 | 原稿对照 | 逐处变化
```

作者可以：

- 直接编辑调整稿；
- 重新生成；
- 补充要求；
- 保留原稿；
- 采用调整稿。

“逐处变化”复用现有差异能力，但用户界面不得出现 `hunk`。

### 采用调整稿

采用前明确：

- 写入修订稿的章节；
- 原稿不变；
- 保留内容是否完整；
- 将生成可恢复版本。

若保留原文缺失，默认不得直接采用。作者必须选择：

- 让系统补回；
- 自己插入；
- 取消该项保留；
- 知情继续。

采用后展示：

- 当前节点完成状态；
- 保留内容检查结果；
- 受影响的后续节点；
- 继续下一项或查看修订稿。

## 9.8 通读工作区

通读以接近普通阅读器的界面展示修订稿，弱化流程和工具栏。

至少支持：

- 章节导航；
- 原稿对照；
- 添加批注；
- 查看当前章节对应的大纲节点；
- 查看保留内容落实情况；
- 标记“这章可以了”或“稍后再改”。

整理建议采用就地提示，作者可以：

```text
现在调整 | 接受现状 | 留到以后
```

定稿不要求建议清零。

## 9.9 整理建议

建议按业务位置和类型分组，例如：

- 与新版大纲有关；
- 与正文衔接有关；
- 与人物或设定有关。

每条建议必须提供：

- 作者可读的建议内容；
- 关联的大纲节点、正文或资料；
- 查看所在位置；
- 根据建议调整；
- 暂不处理。

“根据建议调整”必须返回对应的大纲或正文上下文，不得把作者带入独立的问题关闭流程。

## 9.10 版本

作者可见的版本对象只有：

- 原稿；
- 新版大纲版本；
- 修订稿版本。

要求：

- 原稿始终只读；
- 大纲大范围生成或 AI 调整前后自动留版本；
- 大纲版本可命名；
- 每次采用正文调整稿后生成可恢复版本；
- 版本历史使用业务描述，如“调整‘雨夜决裂’，影响第 18 章”；
- 不展示 checkpoint ID 等内部标识。

## 10. 状态与完成标准

### 10.1 旧稿梳理完成

满足：

- 旧稿大纲已生成；
- 主要节点可追溯到原稿来源；
- 作者可以正常查看和标记保留内容。

不要求作者标记任何保留内容。

### 10.2 新版大纲完成

满足：

- 存在作者确认的大纲版本；
- 作者已知悉尚未安排的保留内容；
- 大纲可以保存或导出。

### 10.3 正文调整完成

满足：

- 作者选择的节点均处于“已完成”或“无需调整”；
- 每次正文写入均进入修订稿并留有恢复版本；
- 未完成节点允许留待以后。

### 10.4 通读定稿完成

满足：

- 作者明确确认当前修订稿版本；
- 不要求整理建议清零；
- 不要求所有原问题关闭；
- 不以健康分作为完成门槛。

## 11. 安全与信任要求

1. 原稿默认只读，任何整理、生成和采用操作均不得覆盖原稿。
2. 所有正文写入只进入修订稿。
3. AI 生成的大纲和正文必须经过作者确认后应用。
4. 作者必须能查看大纲节点和正文调整的原稿来源。
5. 作者必须能撤销大纲编辑，并恢复修订稿版本。
6. 删除新版大纲节点不得删除原稿内容。
7. 取消保留必须由作者显式执行。
8. 系统不能用虚假百分比、循环动画或固定文案伪造进度。
9. 技术失败与创作状态分离，避免把作者的作品节点标记为“失败”。
10. 不向主界面暴露 `issueId`、`stageId`、`runId`、`hunk`、`checkpoint` 或 `quality-gate`。

## 12. 文案规范

### 12.1 推荐用语

```text
整理旧稿
保留情节
保留原文
生成新版大纲
整理这个节点
调整正文
采用这版
查看逐处变化
通读修订稿
确认定稿
整理建议
可恢复版本
```

### 12.2 禁止作为老书主流程文案

```text
救书
写崩
修复问题
关闭问题
质量门
落盘
hunk
checkpoint
健康分
红牌 / 黄牌
第几个问题
```

内部代码、日志和兼容数据可以继续使用技术术语，但作者界面不得直接暴露。

## 13. 现有能力的处理方式

| 现有能力 | v2 中的角色 |
|---|---|
| 全书读取与事实抽取 | 支撑旧稿大纲、人物和设定整理 |
| Story Bible | “资料”中的人物、关系和设定来源 |
| 全书诊断 | 生成整理建议，不作为主阶段 |
| 问题 Dashboard | 降级或重构为“建议”入口 |
| 原文定位 | 大纲节点和正文调整的来源跳转 |
| 局部改写 | 按新版大纲节点生成调整稿 |
| 差异审阅 | “逐处变化”二级视图 |
| checkpoint | 作者可见的“可恢复版本” |
| 最终 audit | 通读阶段的后台建议来源 |
| 旧 issue 工作流 | 兼容历史数据并作为内部能力链，退出默认主导航 |

## 14. MVP 范围

### 14.1 MVP 1：旧稿梳理

必须交付：

- 从现有正文生成旧稿大纲；
- 大纲节点关联来源章节；
- 查看原稿；
- 标记和取消保留情节；
- 框选并保留原文；
- 系统推荐关键原文候选；
- 保留内容抽屉；
- 原稿只读；
- 后台整理状态。

本阶段不要求生成或修改正文。

### 14.2 MVP 2：新版大纲

必须交付：

- 根据旧稿和保留内容生成大纲草案；
- 树形大纲编辑；
- 新增、编辑、移动、删除、合并和拆分节点；
- 节点来源追踪；
- 保留内容覆盖检查；
- AI 调整预览和作者应用；
- 大纲版本；
- 确认和导出大纲。

完成 MVP 2 后，新产品主张应已能独立成立。

### 14.3 MVP 3：正文调整

必须交付：

- 从新版大纲节点创建正文调整单元；
- 生成调整稿；
- 调整稿、原稿对照和逐处变化；
- 保留内容检查；
- 写入修订稿；
- 可恢复版本；
- 节点调整状态；
- 大纲变化后的“需要重新对应”。

### 14.4 MVP 4：通读定稿

必须交付：

- 修订稿阅读模式；
- 大纲节点与正文映射；
- 保留内容校验；
- 批注；
- 就地整理建议；
- 作者确认定稿版本。

## 15. MVP 1 验收标准

MVP 1 完成时，至少满足以下端到端场景：

1. 作者打开已有正文的老书，看到“整理旧稿”入口，不看到问题修复流程。
2. 作者启动整理后，可以看到真实后台状态，并可离开当前页面。
3. 整理完成后，作者看到按层级组织的旧稿大纲。
4. 任一主要大纲节点可以跳到对应原稿章节或片段。
5. 作者可以将一个大纲节点标记为保留情节，并添加说明。
6. 作者可以在原稿中框选文字并标记为保留原文。
7. 作者可以从系统推荐中选择保留原文。
8. 保留内容抽屉能完整列出保留情节和保留原文，并能跳回来源。
9. 取消保留不会删除或修改原稿。
10. 整个流程不会写入原稿正文。
11. UI 不暴露 issue 修复阶段、健康分、红黄牌、hunk、checkpoint 或质量门。
12. 关闭并重新打开项目后，旧稿大纲和保留内容仍然存在。

## 16. MVP 2 验收标准

MVP 2 完成时，至少满足：

1. 作者可以基于旧稿和保留内容生成新版大纲草案。
2. 草案生成前可以选择整理范围、原结局倾向并填写可选要求。
3. 草案不会静默覆盖作者已有大纲版本。
4. 作者可以编辑、移动、新增、删除、合并和拆分节点。
5. 每个非新增节点可查看原稿来源。
6. 页面持续显示保留内容覆盖状态。
7. 删除含保留内容的节点后，相关保留项进入“尚未安排”，原稿不变。
8. AI 调整先提供计划和变化预览，作者应用后才修改大纲。
9. 作者可以撤销、重做并恢复大纲版本。
10. 作者可以在仍有未安排内容时知情确认大纲。
11. 作者可以导出大纲，并选择暂不调整正文。

## 17. 数据与兼容要求

1. 不破坏现有项目、章节、Story Bible、诊断、issue、工作流和正文版本数据。
2. 已有老书项目进入 v2 时，原稿来源必须明确且不可被覆盖。
3. 旧工作流历史可以继续读取，但不再作为 v2 默认主导航。
4. 新版大纲、保留内容和修订稿必须按项目或书籍持久化。
5. 来源引用应优先复用现有稳定章节与原文锚点能力。
6. 正文调整能力后续应支持由大纲节点发起，而非只接受 issue 上下文。
7. Renderer 继续只负责渲染与交互，模型、数据库和文件访问不得进入 Renderer。

## 18. 迁移原则

1. 不在第一批改动中删除现有 issue 工作流。
2. 先实现旧稿大纲与保留内容，使新产品中心成立。
3. 再实现新版大纲编辑器，并将其设为老书默认核心工作区。
4. 之后将现有“定位—改写—审阅—写入”能力抽象为可由大纲节点调用的正文调整能力。
5. 大纲到正文闭环稳定后，再从作者界面移除旧四阶段问题流程和 Dashboard 主入口。
6. 旧项目迁移和旧工作流兼容不得阻塞新项目使用 v2。

## 19. 与现有文档的关系

- 本文档替代 `docs/workflow-guided-workbench.md` 和根目录 `requirement.md` 中关于**老书默认产品主线和主界面**的描述。
- 上述文档关于 Task Runtime、IPC、Renderer 隔离、任务活动、人工确认和安全写入等工程能力仍然有效。
- `docs/workflow-guided-workbench.md` 中 `legacy-book-revision v1` 继续描述当前兼容状态机，不再代表老书 v2 的作者界面。
- 如后续需求发生变化，先更新本文档，再拆实现任务。

## 20. 待后续确认的问题

以下问题不阻塞 MVP 1 的需求成立，但需要在对应阶段开始前确认：

1. 旧稿大纲第一版是否需要“情节段”层级，还是只做“卷 → 关键情节”。
2. 系统推荐关键原文的数量上限和默认筛选策略。
3. 保留原文是否允许作者选择“文字可微调”；当前默认按文字不变处理。
4. 新版大纲导出格式：Markdown、纯文本或同时支持。
5. 修订稿采用“整本派生副本”还是按章节延迟派生。
6. 通读阶段的“定稿”是否生成独立出版版本，还是仅标记当前修订稿版本。
7. 历史老书项目何时自动切换到 v2，是否保留进入旧工作流的辅助入口。
